ESP32 Motor + Screen Board

One ESP32 that runs all six stepper drivers and one round screen, so every other ESP32 stays a screen. It replaces the Pico's logic board while the Pico is out of action. Companion to Driver Board Build: the power board, the driver boards and the motors are built exactly as described there.

Not built or run yet

The firmware for this board compiles but has never run on hardware, and nothing on this page has been checked against a real board. Dry-fit before soldering, find every pin by the label printed next to it (header order differs between makers), and do the checks in Before you power anything first. Channel 5 (Micah) is left off because that driver failed.

How it goes together

Same three domains as the Pico build. The difference: the logic board is an ESP32, it also carries a screen, and the other five ESP32s are the display nodes.

The ESP32's GND goes to the power board's ground rail, the star point, so the drivers read STEP and DIR against the same ground the ESP32 drives them from. Its USB cable goes to the Pi (data and power), not to the charging strip.

Why these pins

D15 is high at boot, which is the released state, so the drivers stay off until the firmware asks. D14 pulses briefly at boot, which is harmless while the drivers are disabled. The pins avoid the screen (D2, D4, D5, D18, D23), the other strapping pins (D0, D12), the flash pins (D6 to D11), the console (RX0, TX0) and the input-only pins (D34 to D39).

One driver channel

All five fitted drivers are wired the same way. The only new part is a 330 Ω resistor in series with every STEP, DIR and ENABLE line, close to the ESP32. A driver that fails can then no longer push real current back into the board. The ENABLE line needs just one resistor, at the ESP32 pin, before it splits to the drivers.

Before you power anything

Do these with everything unplugged and the ESP32 not yet seated, so a fault on the board cannot reach it. They are the checks that would have caught the failure that killed the Pico.

  1. No driver is fitted for channel 5. Leave that socket empty and leave D21 and D22 unconnected.
  2. Vref is set on each fitted driver (about 0.8 V on an R100 board, with the 12 V off). See Setting the current limit.
  3. Continuity from VMOT (the 12 V rail) to every STEP, DIR and ENABLE pad on every driver: none should beep. If one does, that driver is leaking 12 V onto its control pins. Do not fit it.
  4. 3V3 to GND on the logic board: it must not beep, and should read hundreds of ohms or more.
  5. Neighbouring pads. Check every pair of adjacent ESP32 header holes for solder bridges, and each resistor's two legs for a bridge across them.
  6. Motors are plugged in with the 12 V off. Never plug or unplug a motor with the 12 V on: the spike kills the driver.

First power-up

On the Pi. Keep the 12 V off for the first two steps.

  1. Flash the board (see Which firmware), then plug its USB into the Pi.
  2. Stop the controller so the port is free: sudo systemctl stop clockd
  3. Check it answers: .venv/bin/python tools/bench.py --port /dev/ttyUSB0 info (opening the port resets an ESP32; wait a couple of seconds).
  4. Switch on the 12 V, then test one channel at a time: .venv/bin/python tools/bench.py --port /dev/ttyUSB0 check --ch 0
  5. Watch late in status while the screen is drawing. It counts steps that ran behind schedule. Zero, or slowly climbing, is fine. Climbing fast means one ESP32 is not keeping up.

bench.py still prints Pico pin names in its channel labels. Use the table above.

Which firmware

This board

C++, the display-motors PlatformIO environment. It is the display node plus the motors in one program: the step loop runs on core 0, the screen and MQTT on core 1.

pio run -e display-motors -t upload
pio run -e display-motors -t uploadfs

The other five

The normal display node, screen only: pio run -e display-node -t upload.

The serial port carries the motor protocol on this board, so it prints no log. Use the screen or MQTT status to debug the display half.

Untested on hardware. Pin assignments come from firmware/esp32/src/motors.h; the pin names assume the common 30-pin DevKit layout. Check your own board's printed labels first.
